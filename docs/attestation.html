🔐 Cryptographic Attestation & KMS Sealing

Hardware-based proof of execution environment with AWS KMS integration for secure key management

What is Attestation?

Attestation is the process of generating cryptographic evidence that proves the current state of a computing environment. With AWS NitroTPM, we can generate attestation documents signed by AWS that prove:

  • Platform Identity: The code is running on genuine AWS Nitro hardware
  • Boot Integrity: The system booted with expected firmware and kernel
  • Application State: Specific application code and data are loaded
  • Model Authenticity: ML model weights have not been modified

Trust Chain

The attestation document establishes a chain of trust from the AWS Nitro root down to the loaded application and model:

flowchart TB A[AWS Nitro Root Certificate] --> B[Intermediate CA] B --> C[TPM Attestation Key Certificate] C --> D[Attestation Document] D --> E[PCR Values] E --> F[Platform Integrity] E --> G[Application Integrity] E --> H[Model Integrity] style A fill:#ff9900,color:#000 style D fill:#0972d3,color:#fff style H fill:#037f0c,color:#fff

Each link is verified before the measurements it carries are trusted. The attestation document is signed with a key whose certificate chains through an intermediate certificate authority to the AWS Nitro root certificate, so a verifier can confirm the document was produced by genuine Nitro hardware and was not forged by the party that operates the instance. Once the chain is validated, the PCR values inside the document are trusted to describe the three properties the collaboration depends on: platform integrity (firmware, boot manager, and secure-boot state), application integrity (the code that was booted), and model integrity (the Boltz weights measured into PCR16). The browser verifies these values when establishing its trusted baseline, and AWS KMS verifies them again on the key policy before it unseals a secret.

PCR Measurements for Sealing

When sealing data to specific PCR values, we use PCRs 4, 7, 12, and 16 which together establish platform and application integrity:

PCR Measurement Security Purpose
PCR4 Boot Manager Code Ensures the bootloader has not been modified (GRUB, systemd-boot)
PCR7 Secure Boot State Verifies Secure Boot policy is enforced and certificates are valid
PCR12 Kernel Command Line Ensures kernel parameters have not been tampered with
PCR16 Application Data (Boltz Model Hash) Proves the ML model weights are authentic and unmodified

The platform and boot measurements in PCR4, 7, and 12 are fixed at launch and do not change while the instance runs. PCR16 is different: it starts at zero and changes only when the application measures a model into it at startup, so it changes if and only if a different set of weights is loaded and re-measured.

The two keys therefore bind different subsets. The model key binds only the platform and boot measurements (PCR4, 7, and 12): the weights are what get measured into PCR16, so at the moment they are decrypted the model is not yet loaded and PCR16 does not describe it, which makes binding the model key to PCR16 circular. Gating the model key on platform integrity releases the weights only onto a known-good instance. The sequence key binds PCR4, 7, 12, and 16: sequence decryption happens after the model is loaded, so PCR16 is meaningful and commits the sequence to the specific model that will fold it.

AWS KMS Integration

AWS KMS supports condition keys that require specific NitroTPM attestation properties, so a key's use can be conditioned on specific PCR values (e.g. the model weights owner requires that weights only decrypt inside an instance presenting the expected measurements).

Enforcement: explicit Deny, not just Allow

An Allow alone does not guarantee attestation. Some other policy statement or grant could still permit kms:Decrypt. The strong control is an explicit Deny: in IAM/KMS policy evaluation, an explicit Deny overrides every Allow. This project therefore writes both:

  • an Allow that permits kms:Decrypt when the NitroTPM PCRs match, and
  • one explicit Deny per PCR that blocks kms:Decrypt whenever that PCR is missing or different.

As a result, the data can be decrypted only inside an instance presenting the exact expected measurements. This is the theft-protection guarantee for the model weights (and for sealed input sequences).

KMS Key Policy with PCR Conditions (Allow + explicit Deny)

The example below is for the model key (biophysicist), which binds PCR4/7/12 only, never PCR16. The weights are what get measured into PCR16, so at model-decrypt time the model is not yet loaded and PCR16 does not reflect it; binding the model key to PCR16 would be circular. The sequence key (biologist) adds PCR16, because sequences decrypt only after the approved model is loaded.

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowDecryptWithBiophysicistAttestation",
            "Effect": "Allow",
            "Principal": { "AWS": "arn:aws:iam::123456789012:role/BoltzEC2Role" },
            "Action": "kms:Decrypt",
            "Resource": "*",
            "Condition": {
                "StringEquals": {
                    "kms:RecipientAttestation:NitroTPMPCR4":  "YOUR_PCR4_VALUE_HEX",
                    "kms:RecipientAttestation:NitroTPMPCR7":  "YOUR_PCR7_VALUE_HEX",
                    "kms:RecipientAttestation:NitroTPMPCR12": "YOUR_PCR12_VALUE_HEX"
                }
            }
        },
        {
            "Sid": "AllowDecryptWithBiophysicistAttestationDenyUnlessNitroTPMPCR4",
            "Effect": "Deny",
            "Principal": "*",
            "Action": "kms:Decrypt",
            "Resource": "*",
            "Condition": {
                "StringNotEquals": { "kms:RecipientAttestation:NitroTPMPCR4": "YOUR_PCR4_VALUE_HEX" }
            }
        }
        /* ...one such Deny per PCR (4, 7, 12) for the model key;
           the sequence key adds a fourth Deny on PCR16... */
    ]
}
Why one Deny per PCR, and no Null guard: a single multi-key StringNotEquals denies only when every key mismatches, so the policy emits one Deny per PCR to deny if any required PCR is wrong. Each Deny is StringNotEquals with no Null guard: because StringNotEquals is a negated operator, IAM treats a missing key as a match, so the Deny fires both when the PCR is absent (an unattested kms:Decrypt that carries no Recipient) and when it is present but different. An earlier design added Null: {"...": "false"} to scope the Deny to requests that already carry the key. That was a security bug: a plain unattested kms:Decrypt then fell through to the Allow, and the weights (or sequences) could be unsealed with no attestation at all. The Deny is scoped to Action: kms:Decrypt, so key administration and the encrypt side are unaffected without needing a Null carve-out. PCR values are exact SHA-384 hex (96 chars).
Where the principal ARN comes from: the Allow's principal is not a hand-typed value. It is the attested instance role ARN, taken from the signed user_data in the attestation document, so it cannot be widened or mistyped by accident. The EC2 instance role carries no standing IAM kms:Decrypt grant. This key-policy Allow (scoped to that ARN and conditioned on the PCRs) is the only path to decryption, so unsealing requires both the exact principal and a matching attestation.
Key separation: the model CMK (alias/boltz-model-key) is used only for the attestation-gated envelope encryption of the weights. The models S3 bucket uses SSE-S3 (the S3-managed key) for at-rest encryption (not this CMK), so the explicit Deny on the CMK never interferes with S3 reading the (already envelope-encrypted) objects.
Licensing and entitlements: scoping the key policy to the instance role ARN binds decryption to a principal, but it does not count how many instances are running the sealed Boltz model. Licensing and entitlements would require additional tracking of the number of instances running the sealed model, so adding the instance profile ARN directly to the key policy may not be the operationally efficient way to do this — a dedicated entitlement/metering service would track running instances instead.

Computing PCR Values

Reading Current PCR Values

# Read SHA-384 PCR values (used by NitroTPM attestation)
tpm2_pcrread sha384:4,7,12,16

# Output:
#   sha384:
#     4: 0x... (96 hex chars)
#     7: 0x... (96 hex chars)
#    12: 0x... (96 hex chars)
#    16: 0x... (96 hex chars)

PCR Extension Formula

When a PCR is extended, the new value is computed as:

PCR_new = SHA-384(PCR_old || data_to_extend)

Extension is one-way: the new register value is the SHA-384 hash of the current value concatenated with the new measurement, so a PCR can only be appended to and never set to an arbitrary value. Its final value is a tamper-evident summary of everything measured into it, in order. If the boot chain or the model on disk changes, the corresponding PCR no longer matches, and the KMS key policy bound to it stops releasing the secret.

For PCR16, starting from all zeros:

# Initial PCR16 value (all zeros, 48 bytes = 96 hex chars)
PCR16_initial = 0x000...000

# After extension with model hash:
PCR16_final = SHA-384(PCR16_initial || model_hash)

# Example:
# model_hash = "abc123..."  (96 hex chars, SHA-384 of model files)
# PCR16_final = SHA-384(zeros || model_hash)
Important: PCR values are cumulative. If you extend PCR16 multiple times, each extension builds on the previous value. For deterministic results, only extend once at startup.

Implementation Guide

Step 1: Compute Expected PCR Values

1

Deploy your AMI and read the boot PCR values (4, 7, 12) after first boot:

tpm2_pcrread sha384:4,7,12 | tee pcr_boot_values.txt

Step 2: Compute Model Hash

2

Compute the SHA-384 hash of your model files:

python3 -c "
import hashlib
sha384 = hashlib.sha384()
for f in ['boltz1.ckpt', 'boltz1_conf.ckpt', 'ccd.pkl']:
    with open(f'/opt/boltz/cache/{f}', 'rb') as fp:
        sha384.update(fp.read())
print(sha384.hexdigest())
"

Step 3: Compute Extended PCR16

3

Calculate what PCR16 will be after extension:

python3 -c "
import hashlib

# Initial PCR16 (all zeros)
pcr16_initial = bytes(48)

# Your model hash (from step 2)
model_hash = bytes.fromhex('YOUR_MODEL_HASH_HERE')

# Extended value
pcr16_extended = hashlib.sha384(pcr16_initial + model_hash).hexdigest()
print(f'PCR16 Extended: {pcr16_extended}')
"

Step 4: Create KMS Key Policy

4

Create or update your KMS key policy with the PCR conditions:

aws kms put-key-policy \
    --key-id YOUR_KEY_ID \
    --policy-name default \
    --policy file://kms-policy.json

Step 5: Encrypt Sensitive Data

5

Encrypt your sensitive data with the sealed key:

aws kms encrypt \
    --key-id YOUR_KEY_ID \
    --plaintext fileb://secret.txt \
    --output text --query CiphertextBlob > encrypted.b64

Decryption with Attestation

Python Example

import boto3
import base64
import os
import subprocess
import tempfile
from backend.services.attestation import AttestationService

# Initialize services
attestation_service = AttestationService()
kms_client = boto3.client('kms')

def decrypt_sealed_data(encrypted_blob: bytes) -> bytes:
    """Decrypt data whose KMS key policy is conditioned on PCR values.

    KMS never returns bare plaintext when a Recipient attestation is supplied.
    It re-encrypts the plaintext to the ephemeral public key carried in the
    attestation document and returns it as CiphertextForRecipient (a CMS/PKCS7
    envelope), which we unwrap locally with the matching private key.
    """
    # 1. Ephemeral RSA key pair; the PUBLIC key is embedded in the attestation doc.
    priv = subprocess.run(['openssl', 'genrsa', '2048'],
                          capture_output=True, check=True).stdout
    pub = subprocess.run(['openssl', 'rsa', '-pubout', '-outform', 'DER'],
                         input=priv, capture_output=True, check=True).stdout

    # 2. Attestation document carrying the ephemeral public key.
    attestation = attestation_service.generate_attestation(public_key=pub)
    raw_attestation = base64.b64decode(attestation.raw_attestation)

    # 3. Decrypt UNDER ATTESTATION.
    response = kms_client.decrypt(
        CiphertextBlob=encrypted_blob,
        Recipient={
            'KeyEncryptionAlgorithm': 'RSAES_OAEP_SHA_256',
            'AttestationDocument': raw_attestation
        }
    )

    # 4. KMS returns CiphertextForRecipient (NOT Plaintext); unwrap with the private key.
    with tempfile.NamedTemporaryFile(delete=False) as f:
        f.write(priv)
        priv_path = f.name
    try:
        return subprocess.run(
            ['openssl', 'cms', '-decrypt', '-inform', 'DER', '-inkey', priv_path],
            input=response['CiphertextForRecipient'], capture_output=True, check=True
        ).stdout
    finally:
        os.unlink(priv_path)

# Usage
encrypted_data = base64.b64decode(open('encrypted.b64').read())
plaintext = decrypt_sealed_data(encrypted_data)
print(f"Decrypted: {plaintext}")
Note: AWS KMS never returns bare plaintext when an attestation document is supplied as the Recipient. It returns CiphertextForRecipient, the plaintext re-encrypted to the ephemeral public key from the attestation document, which the application unwraps locally with the matching private key held inside the TEE.

Attestation Document Structure

The attestation document from nitro-tpm-attest is a COSE_Sign1 structure containing:

Field Description
module_id Identifier for the NitroTPM module
timestamp Generation time (Unix timestamp)
digest Hash algorithm used (SHA384)
nitrotpm_pcrs Map of PCR index to SHA-384 value
certificate TPM attestation key certificate (DER)
cabundle Certificate chain to AWS Nitro root
public_key Optional: public key for sealed responses
nonce Optional: client-provided freshness nonce
user_data Optional: application-specific data

No self-graded verification fields: the response deliberately does not carry cose_verified / certificate_chain_verified / root_verified. A service grading its own attestation is no evidence. The backend only produces the signed document; the trust decision is made entirely by the relying party (the browser), which parses the COSE_Sign1, verifies the certificate chain link by link, anchors it to the pinned AWS Nitro root CA, and checks the COSE signature itself. The user_data field echoes the signed instance role ARN the browser binds into the KMS key policy.

Verification Workflow (in the browser)

Verification runs entirely in the relying party (the browser) against a pinned copy of the AWS Nitro root CA. The backend never grades its own attestation. The browser fetches the signed document from GET /api/v1/attestation, then:

Verification Code (browser, TypeScript)

The browser verifier is app/frontend/src/services/attestationVerifier.ts. It uses WebCrypto and a pinned root CA (awsNitroRootCa.ts); no backend call is trusted for the verdict.

import { inspectAttestationDocument } from './attestationVerifier'

// `raw` is the base64/CBOR COSE_Sign1 document returned by GET /api/v1/attestation.
const inspection = await inspectAttestationDocument(raw)

// Each step is verified in the browser against the pinned AWS Nitro root:
if (!inspection.coseSignatureValid) throw new Error('COSE signature invalid')
if (!inspection.certificateChainValid) throw new Error('certificate chain broken')
if (!inspection.rootOfTrustValid) throw new Error('not anchored to AWS Nitro root')

// Compare the attested PCRs against the trusted baseline (trust store) the
// relying party maintains locally. Model key: PCR4/7/12; sequence key: + PCR16.
const expected = trustStore.pcr_values // { pcr4, pcr7, pcr12, pcr16? }
for (const [pcr, value] of Object.entries(expected)) {
  if (inspection.pcrs[pcr] !== value) {
    throw new Error(`${pcr} mismatch: expected ${value}, got ${inspection.pcrs[pcr]}`)
  }
}
// All checks passed in the browser. The session may now be trusted and cached.

Security Best Practices

✅ Do

  • Always include a fresh nonce in attestation requests
  • Verify the full certificate chain to AWS root
  • Bind the PCRs each key actually needs: PCR4/7/12 for the model key, plus PCR16 for the sequence key
  • Compute expected PCR values from known-good builds
  • Rotate encrypted secrets regularly
  • Log attestation failures for security monitoring

❌ Avoid

  • Accept attestations without verifying signatures
  • Hardcode PCR values without understanding them
  • Extend PCR16 multiple times per boot
  • Skip certificate chain validation
  • Store expected PCR values in the application itself
  • Ignore attestation timestamp freshness
