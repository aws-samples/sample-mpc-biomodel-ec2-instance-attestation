📦 Packaging with Kiwi

Build attestable Amazon Machine Images (AMIs) using Kiwi-ng from a declarative, version-controlled description

What is Kiwi?

Kiwi-ng is an OS image builder that creates system images from declarative configuration files. It is well suited to creating AMIs for the following reasons:

  • Repeatability: the image is defined declaratively and built the same way every time. Bit-for-bit reproducibility is not automatic; pin package versions if you require it.
  • Version Control: Image configuration is tracked in Git alongside application code
  • Customization: Full control over packages, services, and configurations
  • Automation: Integrates into CI/CD pipelines

Image Configuration (config.xml)

The image is described declaratively in kiwi/config.xml. Rather than reproduce the whole file, the snippets below call out the parts that define what kind of image this is: the base OS, the two operator-access profiles, the sealed boot type, and the packages that matter for attestation. It is a dm-verity sealed, read-only overlay-root appliance booted by systemd-boot (a Unified Kernel Image), not a GRUB image.

Base OS and build profiles

The base is a minimal Amazon Linux 2023 (the core and ami-minimal collections), pulled from a GPG-checked mirror list. Exactly one profile is selected per build with the kiwi-ng --profile flag: prod is the Zero Operator Access (attestable) image, and foa is the Full Operator Access image for dev and test only.

<image schemaversion="7.5" name="boltz-protein-folding-attestable">
    <profiles>
        <profile name="prod" description="Production, attestable, no operator access (no SSH/SSM)"/>
        <profile name="foa"  description="Full Operator Access, SSH/SSM enabled (DEV/TEST ONLY)"/>
    </profiles>

    <!-- Minimal Amazon Linux 2023 base, from a GPG-checked mirror list -->
    <repository priority="2" package_gpgcheck="true" sourcetype="mirrorlist" customize="add-gpg-key.sh">
        <source path="https://cdn.amazonlinux.com/al2023/core/mirrors/latest/$basearch/mirror.list"/>
    </repository>

Zero Operator Access (prod) vs Full Operator Access (foa)

This is the security-critical difference between the two profiles. The prod (Zero Operator Access) profile removes every remote-access path, so a running instance cannot be logged into or modified. The foa profile adds SSH, the SSM Agent, and debug tooling, which is why it is restricted to dev and test. The prod kernel command line also disables the serial console getty (systemd.getty_auto=false); foa is identical except it sets systemd.getty_auto=true.

<!-- prod (Zero Operator Access): strip every remote-access path -->
<packages type="image" profiles="prod">
    <ignore name="openssh-server"/>
    <ignore name="amazon-ssm-agent"/>
    <ignore name="cloud-init"/>
    <ignore name="ec2-instance-connect"/>
    <ignore name="update-motd"/>
</packages>

<!-- foa (Full Operator Access, DEV/TEST ONLY): add SSH, SSM and debug tools -->
<packages type="image" profiles="foa">
    <package name="openssh-server"/>
    <package name="amazon-ssm-agent"/>
    <package name="cloud-init"/>
    <package name="ec2-instance-connect"/>
    <package name="vim-minimal"/>
    <package name="htop"/>
    <package name="strace"/>
    <package name="tcpdump"/>
</packages>

Sealed boot type (dm-verity + systemd-boot)

Both profiles use the same appliance boot type: a read-only erofs overlay root with verity_blocks="all" (so the whole root is dm-verity sealed and boot panics on corruption), booted by a systemd-boot Unified Kernel Image under UEFI. editbootinstall runs edit_boot_install.sh, which computes the boot PCRs over that UKI.

<preferences profiles="prod">
    <type image="oem" filesystem="xfs" firmware="uefi"
          overlayroot="true"
          overlayroot_readonly_filesystem="erofs"
          verity_blocks="all"
          kernelcmdline="console=ttyS0 rd.shell=0 systemd.getty_auto=false rd.kiwi.verity_options=panic-on-corruption"
          editbootinstall="edit_boot_install.sh">
        <oemconfig><oem-resize>false</oem-resize></oemconfig>
        <bootloader name="systemd_boot" timeout="10"/>
        <initrd action="setup"><dracut uefi="true"/></initrd>
        <size unit="G">40</size>
    </type>
</preferences>

Key packages

The base package set (shared by both profiles) pulls in the boot chain, the dm-verity and overlay support, the attestation tooling, the Python runtime, and the NVIDIA/CUDA build dependencies. GRUB is explicitly excluded, since systemd-boot is the bootloader.

<packages type="image">
    <archive name="overlay.tar.gz"/>              <!-- app bin, systemd units, config -->

    <!-- Boot chain: systemd-boot UKI (no GRUB) -->
    <package name="kernel"/>
    <package name="systemd-boot"/>

    <!-- dm-verity sealed / erofs overlay root -->
    <package name="veritysetup"/>
    <package name="dracut-kiwi-verity"/>
    <package name="dracut-kiwi-overlay"/>

    <!-- NitroTPM attestation + the KMS Recipient flow -->
    <package name="aws-nitro-tpm-tools"/>
    <package name="tpm2-tools"/>
    <package name="openssl"/>

    <!-- Boltz application runtime -->
    <package name="awscli"/>
    <package name="python3"/>
    <package name="python3-pip"/>

    <!-- NVIDIA driver + CUDA build deps (driver and CUDA are installed in config.sh) -->
    <package name="kernel-devel"/>
    <package name="gcc"/>
    <package name="make"/>
    <package name="dkms"/>

    <!-- GRUB explicitly excluded; systemd-boot is the bootloader -->
    <ignore name="grub2-tools"/>
    <ignore name="grub2-efi-x64"/>
</packages>

The prod image is finished off by two post-install scripts: config.sh creates the unprivileged boltz service user (there is no ec2-user outside foa), installs the NVIDIA driver and the Python dependencies into the system interpreter, and enables the backend services; and images.sh clears caches, temp files, and logs just before the image is created.

Building the Image

Step 1: Install Kiwi Dependencies

cd packaging-kiwi-ng/scripts
sudo ./install-deps.sh

install-deps.sh installs:

  • Kiwi-ng (kiwi-cli, python3-kiwi, kiwi-systemdeps-core) and qemu-img
  • veritysetup and erofs-utils for the dm-verity sealed, erofs overlay root
  • cargo and aws-nitro-tpm-tools
Note: install-deps.sh does not install the AWS CLI. The snapshot upload uses coldsnap, and coldsnap now needs a newer Rust toolchain than the distro cargo can provide. In the CodeBuild pipeline the buildspec installs a current rustup stable toolchain plus the C build deps (gcc, gcc-c++, make, cmake, perl, nasm) and then runs cargo install --locked coldsnap before registering the AMI.

Step 2: Build the Image

sudo ./build.sh

The build process:

  1. Creates a temporary root filesystem
  2. Installs packages from repositories
  3. Copies application code and overlay files
  4. Runs config.sh for system configuration
  5. Runs images.sh for final cleanup
  6. Creates a bootable disk image
Build Time: A full build typically takes 15-30 minutes depending on your system and network speed.

Step 3: Upload to AWS

./upload-ami.sh

This script does not use S3 or an EC2 image-import task. It:

  1. Builds and installs coldsnap if it is not already present
  2. Uploads the raw image directly to an EBS snapshot with coldsnap (EBS Direct APIs)
  3. Registers an AMI from that snapshot with aws ec2 register-image, setting --tpm-support v2.0 and --boot-mode uefi
  4. Tags the AMI and snapshot, then outputs the AMI ID and the recorded PCR measurements

How the build actually runs (AWS CodePipeline / CodeBuild)

There is no GitHub Actions workflow in this repository. The AMI is built by an AWS CodePipeline / CodeBuild project defined in CDK (cdk/lib/constructs/codebuild.ts). kiwi-ng cannot build a disk image inside a container, so the build runs on a reserved-capacity EC2 fleet (LINUX_EC2, Amazon Linux 2023) where loop devices and dm-verity work natively. The project uses an IAM role (EBS Direct API, ec2:RegisterImage, and SSM write for the AMI id and PCR trust store), never static access keys. The buildspec:

# install phase (buildspec, on the AL2023 EC2 fleet)
dnf install -y kiwi-cli python3-kiwi kiwi-systemdeps-core \
    python3-poetry-core qemu-img veritysetup erofs-utils git jq aws-nitro-tpm-tools
dnf install -y gcc gcc-c++ make cmake perl nasm
# Distro cargo (rustc 1.92) is too old for coldsnap's deps, so use rustup stable:
curl --proto "=https" --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y \
    --default-toolchain stable --profile minimal
source "$HOME/.cargo/env"
cargo install --locked coldsnap

# build + upload phases
./packaging-kiwi-ng/scripts/build.sh      --profile "$BUILD_PROFILE"   # prod or foa
./packaging-kiwi-ng/scripts/upload-ami.sh                              # coldsnap + register-image
BUILD_PROFILE: the CodeBuild environment variable BUILD_PROFILE selects the kiwi profile. It defaults to prod, the attested Zero Operator Access image (no SSH, no SSM agent, no cloud-init, dm-verity read-only root). Set it to foa for a debuggable image with SSH and the SSM Agent (dev/test only).

Overlay Files

Files in the overlay/ directory are copied directly to the root filesystem. This is useful for:

  • Systemd service files
  • Application configuration
  • Udev rules
  • Custom scripts

Example: Systemd Service

# overlay/etc/systemd/system/boltz-backend.service
[Unit]
Description=Boltz Protein Folding Backend API
After=network.target
# boltz-config.service fetches CORS_ORIGINS from SSM and writes /etc/boltz/environment
# before we start. Wants (not Requires) so a config-fetch failure does not block boot.
After=boltz-config.service
Wants=boltz-config.service

[Service]
Type=simple
User=boltz
Group=boltz
WorkingDirectory=/opt/boltz/app
Environment=PYTHONPATH=/opt/boltz/app
Environment=PATH=/usr/local/bin:/usr/bin:/bin
Environment=MODEL_PATH=/opt/boltz/models
# BOLTZ_CACHE must equal MODEL_PATH so the CLI loads weights from exactly the
# directory attestation measures into PCR16.
Environment=BOLTZ_CACHE=/opt/boltz/models
EnvironmentFile=-/etc/boltz/environment
# System python (there is no venv); the boltz user reaches the TPM via the tss group.
ExecStart=/usr/bin/python3 -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 --workers 1
SupplementaryGroups=tss
Restart=always

[Install]
WantedBy=multi-user.target

Example: Application Config

# overlay/etc/boltz/config.yaml
server:
  host: 0.0.0.0
  port: 8000
  workers: 1

model:
  path: /opt/boltz/models   # same dir attestation measures into PCR16
  device: auto              # auto, cpu, or cuda
  max_sequence_length: 2048

attestation:
  enabled: true
  tpm_device: /dev/tpmrm0
  pcr_banks:
    - sha256
  validity_seconds: 300

logging:
  level: INFO
  format: json

In-image firewall (fail-closed nftables)

The firewall is a static nftables ruleset (overlay/etc/nftables/boltz-firewall.nft), not firewalld. It is loaded once at boot by boltz-firewall.service, ordered Before=network-pre.target, so the rules are in place before any interface is configured. The base chain policy is drop and there is no zone model, so coverage is interface-agnostic: any ENI, the primary one or a hot-plugged secondary, is denied by default and only the Boltz backend port (8000), loopback, DHCP, IPv6 neighbor discovery, and return traffic are allowed (SSH is added only under the foa profile). Port 8000 is the only listening service: the frontend is hosted on Amplify and reaches the instance through API Gateway, a VPC Link, and the internal NLB, so nothing else is served from the instance. This is deliberate: firewalld is a runtime daemon that regenerates its rules from config at every boot, so a failed daemon start would mean no rules and an open instance. A static ruleset in the dm-verity sealed rootfs is the enforcement artifact itself, so it is part of the attested image and cannot be altered at runtime. config.sh validates the final ruleset with nft -c at build time, so a malformed firewall fails the AMI build rather than the boot. The firewall is the in-TEE control; the AWS Security Group is a separate hypervisor-level backstop that sits outside the attestation boundary.

# overlay/etc/nftables/boltz-firewall.nft (excerpt)
table inet boltz_filter {
    chain input {
        type filter hook input priority 0; policy drop;
        ct state established,related accept
        ct state invalid drop
        iif "lo" accept
        tcp dport 8000 accept
        # ssh (tcp/22) is uncommented by config.sh only for the foa profile
    }
    chain forward { type filter hook forward priority 0; policy drop; }
    chain output  { type filter hook output  priority 0; policy accept; }
}

PCR Values in AMI

The platform and boot PCRs (PCR4, 7, 12) are deterministic for a given image: they are fixed at build time and computed over the systemd-boot Unified Kernel Image (UKI) by edit_boot_install.sh using nitro-tpm-pcr-compute, and written to pcr_measurements.json. PCR16 is different: it is a runtime measurement (see the note below the table), not part of the AMI.

PCR Determined By Changes When
PCR4 UEFI boot application: the systemd-boot UKI (not GRUB, which is excluded) Kernel, initrd, or UKI contents change
PCR7 Secure Boot state, computed over the same UKI Secure Boot config or the signed UKI changes
PCR12 Kernel command line kernelcmdline in config.xml changes
PCR16 Runtime: SHA-384 of the Boltz weights, extended at model load The loaded model changes; all-zeros when no model is present
Important: PCR16 is extended at model load with the SHA-384 of the Boltz weights. With no model present at boot it is deliberately left unextended (its reset value, all-zeros), so it is not deterministic from the image configuration. After building a new AMI, record the new boot PCRs and update any KMS key policies that reference them.

Recording PCR Values

The prod image has no SSH, no ec2-user, and no SSM agent, so you do not log in to read PCRs. The boot PCRs (4, 7, 12) are produced at build time in pcr_measurements.json (also written to the SSM trust-store parameter by the pipeline), and the running instance reports all PCRs through the attestation API. Only a foa (dev/test) image can be reached over SSH.

# Boot PCRs (4, 7, 12): from the build artifact, no login required
cat packaging-kiwi-ng/output/pcr_measurements.json

# All PCRs, including the runtime PCR16, from the attestation document
curl -s https://<backend>/api/v1/attestation | jq '.pcr_values'

# foa (dev/test) images only: read PCRs directly on the instance
# ssh ec2-user@instance-ip
# tpm2_pcrread sha384:4,7,12,16

Best Practices

  • Version Everything: Tag your Kiwi configs alongside application versions
  • Minimize Image Size: Remove unnecessary packages and clean caches
  • Security Hardening: Remove default credentials, disable root login
  • Test Images: Always test new AMIs before production deployment
  • Document PCR Values: Keep a record of expected PCR values per AMI version
  • Automate Builds: Use CI/CD to ensure consistent builds
