🧬 Boltz Protein Folding with Attestation

Secure protein structure prediction using the Boltz model with hardware-based attestation on AWS EC2 instances with NitroTPM

Application Overview

Boltz is an open machine learning model for protein structure prediction, the task commonly known as protein folding: given an amino acid sequence, it predicts the protein's 3D folded structure. Running it in practice brings together two independently owned assets. The model is a checkpoint of the Boltz base model fine-tuned on proprietary structural data, such as crystallography and cryo-EM measurements, at substantial expense; it is owned by the pharmaceutical or biotechnology organization that produced it, represented in this sample by the computational biophysicist persona, and is treated as core intellectual property. The inputs are the sequences to be folded, owned by the research organization that generated them and represented in this sample by the computational biologist persona: candidate protein sequences, whole-exome panels, variant-call files, and other genomic assays that can represent years of research and carry regulatory obligations.

For inference to run, the model weights and the input sequences must reside on the same accelerated (GPU) backend and be present together in plaintext. In many collaborations that co-location cannot be achieved by sharing the assets directly. The biophysicist cannot transmit a copy of the weights, because a single exfiltrated checkpoint is fully functional and the disclosure cannot be undone. The biologist cannot expose the sequences to the operator or a co-tenant, because that disclosure can be irreversible and can breach a patent or a compliance obligation. Here the operator is the infrastructure host: the party that owns the AWS account and runs the EC2 instance and Boltz compute, as distinct from the two data owners. Neither party fully trusts that operator, so neither is willing to release its asset to it in plaintext.

This is a reference sample that demonstrates how the two parties can collaborate by sharing their assets sealed to a trusted execution environment (TEE), never in plaintext to each other or to the operator. Each party seals its asset to the TEE: an immutable EC2 instance, operating under zero-operator access, whose integrity is proven by Amazon EC2 instance attestation. As AWS defines it, attestation "is a process that allows you to cryptographically prove to any party that only trusted software, drivers, and boot processes are running on an Amazon EC2 instance"; it is powered by the Nitro Trusted Platform Module (NitroTPM) and Attestable AMIs. AWS KMS unseals a secret only when the instance's attested Platform Configuration Register (PCR) values match a known-good measurement, with the loaded Boltz weights measured into PCR16. The model weights and the input sequences are therefore decryptable only inside the TEE, GPU memory included, which is the single place they come together for inference and whose software state both parties can independently verify.

System Architecture

A FastAPI backend runs on a NitroTPM-attested EC2 instance for ML inference and attestation; the React/Vite UI is hosted on AWS Amplify and reaches the backend through API Gateway (Cognito JWT) + VPC Link + an internal NLB. The EC2 instance is placed in an isolated private subnet with no route to the internet: the VPC is provisioned with no public subnets and no NAT gateway, and the instance reaches AWS services only through VPC endpoints (S3, KMS, STS, and others).

The design keeps the attested backend private and performs every sensitive operation inside it. The React user interface hosted on AWS Amplify is the only public surface. A request from either role carries an Amazon Cognito JSON Web Token and reaches the backend through Amazon API Gateway, a VPC Link, and an internal Network Load Balancer; the EC2 instance has no public address, so the operator cannot expose it to the internet directly. Inside the instance, the FastAPI server routes prediction requests to the Boltz service and attestation requests to the attestation service, which reads the NitroTPM device at /dev/tpmrm0. Both protected assets are stored sealed in Amazon S3: the model weights in the boltz-models-* bucket and the input sequences in the boltz-sequences-* bucket, each encrypted with its own AWS KMS key. The sequences are encrypted client-side (a KMS Encrypt call from the browser), and the model weights are envelope-encrypted cloud-side by a CodeBuild model-update workflow, because the weights exceed the size a direct KMS Encrypt call can handle. The backend fetches only ciphertext from S3 and unseals it through an attestation handshake with AWS KMS, which releases a secret only when the instance's PCR values match the key policy and never returns bare plaintext to the caller. The role flows below and the Attestation page describe this handshake in detail. Unsealing therefore happens inside the trusted execution environment and nowhere else, so plaintext weights and sequences exist only in the instance's host and GPU memory. The instance is therefore the trusted execution environment in which the two assets are combined, and AWS KMS is the verifier that enforces its integrity.

Transport on the last leg (out of scope for this sample): The client-to-API Gateway hop uses HTTPS, but the private integration from Amazon API Gateway through the VPC Link and the internal Network Load Balancer to the EC2 backend on port 8000 is HTTP within the VPC. The sensitive assets themselves are protected end to end at the application layer: sequences and model weights are sealed with AWS KMS and are unsealed only inside the attested instance, so they never traverse this leg in plaintext. Even so, a production deployment should terminate TLS on this hop as well, so that request metadata, authorization tokens, and prediction responses are also encrypted in transit. Provision a certificate with AWS Certificate Manager (ACM) and serve the backend behind a TLS listener. This sample leaves the leg as HTTP to stay focused on the attestation and sealing mechanism.

Roles and protected intellectual property

The reference sample protects two separate pieces of intellectual property, each owned by a different organization. In both flows, attestation is the first step: you verify the backend's PCRs and bind a KMS key policy to them before any secret is sealed, so that data can be decrypted only on a backend whose measurements you already trust. The attestation mechanism these flows rely on, including the PCR measurements, the trust chain to the AWS Nitro root, and the KMS key-policy conditions, is described in detail on the Attestation page.

This flow shows how the pharmaceutical or biotechnology organization publishes its fine-tuned weights without exposing them to the operator. Attestation is the first step: the biophysicist connects to the backend, receives a COSE-signed attestation document carrying the instance's PCR values (the platform and boot measurements in PCR4, 7, and 12 are fixed at launch and do not change thereafter, while PCR16 changes only when a different model is loaded and re-measured into it), verifies the signature and certificate chain against the AWS Nitro root, and records the measurements as the trusted baseline in the browser. Only then does the biophysicist bind the model key policy (alias/boltz-model-key) to the attested platform and boot measurements, PCR4, 7, and 12, so the weights are released only onto an instance whose platform integrity is proven. The model key is deliberately not bound to PCR16: the model weights are what get measured into PCR16, so at the moment the weights are decrypted the model is not yet loaded and PCR16 does not describe it, and binding the model to its own not-yet-loaded measurement would be circular. PCR16 instead gates the sequence key described below, which commits a submitted sequence to the specific model that is loaded. A CodeBuild workflow then downloads the Boltz base model, envelope-encrypts the weights with the model key, and stores the ciphertext in the models S3 bucket; the plaintext weights exist only inside the workflow and, later, the attested instance. To deploy, the backend fetches the ciphertext and calls AWS KMS with the attestation document attached as the recipient. AWS KMS never returns the data key in the clear; only if the instance's PCRs still match the policy does it return the data key encrypted to the ephemeral public key of the attested EC2 instance from the attestation document, which the instance unwraps with the matching private key held inside the TEE and then uses to decrypt the weights. The weights are therefore unsealed on no other machine. The backend then re-extends PCR16 with the hash of the loaded weights, making the identity of the running model part of the attested state that the biologist verifies before submitting a sequence.

This flow shows how the research organization submits a proprietary sequence for folding without disclosing it to the operator. As before, attestation is the first step: the biologist verifies the backend's attestation document and binds the sequence key policy (alias/boltz-sequence-key) to the attested PCRs, which include PCR16 and therefore commit to the specific model that is loaded. The biologist then seals the sequence on the client by encrypting it with the sequence key under a fixed encryption context, and uploads only the ciphertext to the sequences S3 bucket. To run a prediction, the backend calls AWS KMS with the attestation document attached; AWS KMS never returns the plaintext sequence directly. Only if the running instance still matches the policy does KMS re-encrypt the sequence to the ephemeral public key from the attestation document and return it wrapped as CiphertextForRecipient, which the instance unwraps with the matching private key held inside the TEE. The sequence is unsealed inside the instance, folded on the GPU, and returned as a PDB structure with a pLDDT confidence score. Because the measured boundary is the entire instance, the sequence and the weights come together in plaintext only in host and GPU memory that both organizations have attested, and the operator has no path to either asset.

Key Components

The backend is organized as a small set of services behind the FastAPI server. The attestation service produces the signed measurements (the attestation validator parses them for the document it returns), while the trust decision itself is made by the relying party in the browser, and the Boltz service performs inference once a secret has been unsealed. The routes below are the public API surface reached through API Gateway.

Security Model

The diagram maps the primary threats to this collaboration to the measured controls that address them. The mechanisms follow.

flowchart LR subgraph "Threats Mitigated" T1[Model Tampering] T2[Code Modification] T3[Replay Attacks] T4[Unauthorized Access] end subgraph "Protections" P1[PCR16 Model Hash] P2[PCR0-12 Boot Measurements] P3[Nonce in Attestation] P4[KMS PCR Conditions] end T1 -.-> P1 T2 -.-> P2 T3 -.-> P3 T4 -.-> P4 style P1 fill:#037f0c,color:#fff style P2 fill:#037f0c,color:#fff style P3 fill:#037f0c,color:#fff style P4 fill:#037f0c,color:#fff
  • Model tampering: if the weights on disk are swapped or modified, the SHA-384 hash extended into PCR16 changes, the attestation no longer matches the bound key policies, and AWS KMS refuses to decrypt. A substituted model cannot be used to process either party's data.
  • Code modification: the platform and boot measurements in PCR0 through PCR12 change if the firmware, boot manager, secure-boot state, or kernel command line is altered, so a backend running modified code fails attestation and cannot obtain the data keys.
  • Replay attacks: each attestation request includes a fresh nonce that is bound into the signed document, so the operator cannot capture a valid attestation from a good instance and replay it from a compromised one.
  • Unauthorized access: decryption is gated by KMS key-policy conditions on the attested PCR values, expressed as an explicit Deny, so possession of a credential is not sufficient. The request must originate from an instance in the exact measured state.
